SmartHub Diagnostics – Session Memory
Last updated: 2026-05-04

Overview
- Desktop companion app for Android diagnostics with a Node.js + TypeScript (Express) backend, a simple HTML/JS frontend, optional Windows/Python helper tools, and a small on‑device Android app that works only when the phone is connected to the desktop via USB/ADB.
- Uses ADB, fastboot, and local Python tools (for APK security scan) to run offline checks.
- Supports cloud persistence via Supabase for diagnostic history/autosave (authenticated user scope).
- Target users: phone repair technicians; focus on truthful diagnostics with offline-first collection and optional cloud-backed history.

Important limitation (Android security model)
- “Auto install / silent install” is not possible using only MTP file copy.
- Without ADB (or Device Owner / MDM privileges), the install step still requires user interaction on the phone (tap the APK and confirm).

Heuristics summary (src/heuristics.ts)
- analyzeBattery(batteryDump):
	- Extracts current battery level and temperature from dumpsys battery.
	- Emits low-severity snapshot findings used for reporting; threshold-based severity (overheating, low level, health and cycle-count interpretation) is implemented in the /collect pipeline (src/routes/collectRoutes.ts).

- analyzeBatteryConnection(batteryDump, batteryDump2):
	- Compares two battery samples collected ~1s apart to detect unstable/potentially-intermittent battery/power readings.
	- Flags strong indicators like battery present flip, charging-state flip, and unusually large voltage jumps.
	- Used by /collect to set diagDetails.battery.connectionSuspected and raise the battery stage attention state.

- analyzeBatteryConnectionSeries([batteryDump, batteryDump2, batteryDump3]):
	- Series-based (3-sample) battery/power instability detector with stricter thresholds to reduce false positives.
	- Used by /collect when batteryDump3 is available; falls back to analyzeBatteryConnection otherwise.
- analyzeStorage(df):
	- Scans df -h style output and flags user-writable partitions nearing full as "storage-pressure-*" findings (medium/high).
	- /collect uses these findings to mark the System stage attention when storage is near full.

- analyzeMemoryHealth(procMeminfo):
	- Uses /proc/meminfo to detect memory pressure ("memory-tight" / "memory-low") and to emit a snapshot when OK.
	- /collect uses this to include memory pressure in the System stage.
- analyzeLogs(logcat):
	- Detects recent crash/ANR patterns and display pipeline errors (SurfaceFlinger / GPU / HWC) from logcat.
	- Deeper filesystem/integrity and OS health heuristics (fs errors, dm-verity, core-service crashes) are implemented in the /collect pipeline (OS / filesystem stage) rather than in this module.

- analyzeUsbInstability({ logs, warnLogs, kernelLogs }):
	- Scores repeated USB/ADB disconnect/reset evidence in logs (strict thresholds to reduce false positives).
	- /collect surfaces this as an attention hint in the Connectivity stage.

- analyzeThermalThrottling(thermalDump, logs?, warnLogs?):
	- Uses dumpsys thermalservice (Thermal Status) plus log evidence to detect throttling/overheat conditions.
	- /collect surfaces this as an attention hint in the Battery stage.

- analyzeRadioModemStability({ logs, warnLogs, crashLogs, kernelLogs }):
	- Detects modem/baseband/radio crash-loop patterns (RIL/IMS/subsystem restart hints).
	- /collect surfaces this as an attention hint in the Connectivity stage.

- analyzeApps(apps, permsByPkg):
	- Walks installed apps and their requested permissions to emit high/medium severity findings for apps that request risky or sensitive permissions.
	- Used by /apps/:id as an additional, permission-only signal alongside deep APK scan results.

App security heuristics (also in src/heuristics.ts)
- assessAppRisk(perms), classifyAppRisk(perms), scoreAppRisk(perms, path?):
	- Classify apps into safe / moderate / risky based on requested permissions, with explicit lists for high-impact permissions (DEVICE_ADMIN, SYSTEM_ALERT_WINDOW, BIND_ACCESSIBILITY_SERVICE, SMS/Call, etc.).
	- scoreAppRisk adds a 0–100 risk score, giving higher weight to risky permissions and slightly discounting apps that live under system/product partitions versus /data.
- detectSuspiciousApps(apps, permsByPkg, installerMap?):
	- Uses package-name patterns (cleaner/booster/optimizer, mod/crack/hack, known ad SDKs, fake system updates, etc.), permission combinations (overlay + internet + background), accessibility/admin rights, and installer source to flag adware/malware-style apps.
	- Incorporates a small allowlist of trusted prefixes (com.google., com.android., major OEMs and browsers) and a map of known fake/modified popular apps.

- Endpoints (overall API surface)
		- GET /device – list devices via `adb devices -l`, enrich with model/brand from getprop.
		- GET /mobile-app-state/:id – checks via ADB whether the SmartHub Android app package (com.smarthub.diagnostics) is installed and currently running on the handset; the frontend uses this to block full diagnostics until the on-device app is present and open.
		- GET /connection-check – runs `adb devices -l`, `fastboot devices` and (on Windows) a PowerShell `Get-PnpDevice` query for MTP/portable devices. Returns:
			- adb: { ok, devices[], error? }
			- fastboot: { ok, devices[], error? }
			- hostUsb: { platform, portableDevices[], transportDevices[], sample?, error? } – host-side view of phones that show up in Windows (Portable/MTP or transport-level USB) even when ADB is empty.
			- summary: human-readable connection status that explains what the PC can see (ADB, fastboot, MTP, or nothing).
			- signals (deep=1 only): extra evidence used to improve explainability and accuracy.
				- signals.fastboot: [{ deviceId, vars?, error? }]
				- signals.adb: { deviceId, state, bootCompleted?, bootReason?, verifiedBootState?, vbmetaDeviceState?, battery?, dataPartitionUsePct?, logEvidence? }
			- bsodAnalysis: { category, primaryReason?, confidence, reasons[], part1? } → heuristic cause for blue/blank screen based on ADB/fastboot/host USB visibility and (when available) evidence signals.
				- part1: { category, primaryReason?, confidence, reasons[] } where category is one of: System Errors / Application Conflicts / Hardware Malfunction / Overheating / Insufficient Storage.
		- POST /launch-bsod-gui – launches external BSOD desktop helper (`bsod-diagnostic/bsod_gui.py`) via Python.
		- GET /collect/:id – main diagnostic pipeline per device:
			- Collects dumps: getprop, dumpsys battery (two samples: batteryDump + batteryDump2), df -h, /proc/meminfo, dumpsys display, logcat (error buffers) + logcat WARN (warnLogs), plus best-effort sensor/camera/connectivity/features dumps.
			- Uses heuristics from src/heuristics.ts (analyzeBattery, analyzeStorage, analyzeLogs) to build findings.
				- Extracts OS/build info (Android version, fingerprint, tags → custom/test build, verified boot state, bootloader lock).
			- Display metrics: resolution from dumpsys display; estimates diagonal inches + area cm² using DPI from dumpsys or density props (ro.sf.lcd_density / ro.display.lcd_density).
				- Battery metrics: level, temp, health, capacity (capacity or charge_counter /1000 or /sys/class/power_supply/battery/charge_full_design), cycle_count (from dumpsys or /sys/.../cycle_count), simple charging efficiency label, and an inferred battery technology from dumpsys or /sys.
					- Extra power-path fields (best-effort): present, voltageMv, currentNowRaw, status, isCharging.
					- Intermittency signals: connectionSuspected (from batteryDump vs batteryDump2) and strict log evidence (powerLogSuspected/powerLogScore/powerLogHints from WARN/ERROR logs).
				- Connectivity metrics: combines dumpsys connectivity + pm list features for Wi-Fi, Bluetooth, NFC, GPS, mobile.
				- Sensors, camera, hardware, system, OS stages all summarized into diagStages + diagDetails – including RAM estimate from /proc/meminfo, feature-based hardware presence, and OS/filesystem integrity hints (EXT4/F2FS errors, dm-verity warnings, core-service crashes).
			- Touch / ghost touch stage:
				- TouchStageDetails: { hasTouchDriverErrors?, hasInputAnomalies?, isChargingDuringLogs? }.
				- Scans logcat for touch driver/controller errors (touchpanel/fts/synaptics/goodix/elan/atmel, InputReader failures) and input anomalies (InputDispatcher unresponsive, pointer cancel spam, “touch event rate too high”).
				- Uses battery dumps to detect if device was charging during logs.
				- diagStages.touch = { ok, label "Touch / ghost touch", details joined from reasons }.
				- Returns a full payload used by js/diagnostics.js: propsDump, battery/storage/memory/display dumps, logs, findings array, and structured diagStages + diagDetails.
		- GET /screenshot/:id – raw screencap PNG (uses binary screencap from src/adb.ts).
		- POST /screen-test/:id – guided screen test capture:
			- Calls screencap(id) to get PNG buffer.
			- Saves to windows-app/bin/Release/net8.0-windows/win-x64/publish/screenshot/<safeDeviceId>/<timestamp>.png.
			- Returns { ok, imagePath: /screen-test-image/<safeId>/<file>, imageUrl }.
		- GET /screen-test-image/:deviceId/:file – serves PNG from the above screenshot folder.
		- GET /display-state/:id – returns raw dumpsys display + SurfaceFlinger for advanced display debugging.
		- GET /on-device-report/:id – fetches JSON diagnostics written by the SmartHub Mobile Diagnostics Android app (if present) for combined desktop + on‑device analysis.
		- GET /deep-scan/:id – lightweight health overview for the connected device; returns small results by default and supports raw payloads via ?raw=1.
		- GET /screen-visual-check – optional host-side visual check of the phone screen using the PC webcam and `bsod-diagnostic/phone_screen_diag.py`; no USB debugging required, returns JSON analysis (category + hints like cracks/banding/overheat).
		- GET /screen-camera-snapshot – same helper as /screen-visual-check but also saves the sharpest frame under the Windows app screenshot folder and returns { ok, imagePath, imageUrl, analysis } so the UI can show a "screenshot" even when adb screencap is not available.
		- Both endpoints resolve a Python executable via a small defaultPythonExe helper that prioritises: (1) `SMART_HUB_PYTHON_EXE` when set (typically by the Windows shell/installer), (2) a local `.venv` under the app install root (SMARTHUB_HOME or process cwd), and finally (3) `python`/`python3` on PATH. This makes camera-based checks work both when launched from the Windows shell and when running the backend directly via `npm run dev`, as long as Python 3.8+ with opencv-python and numpy is installed in one of those locations.
			- GET /file-scan/:id – heuristic user-storage scan:
				- Walks `/sdcard` or `/storage/emulated/0` (limited depth) and counts total files.
				- Flags paths by extension/keywords (.apk, .dex, .jar, .exe, hack/crack/mod/keygen/etc) and returns counts + up to 50 sample paths.
			- GET /app-usage/:id – app size/usage view:
				- Lists apps and correlates them with du -k -s output for `/data/app`, `/data/user/0` (or `/data/data` fallback).
				- Returns codeBytes/dataBytes/totalBytes per app and a note when /data is not readable (non-rooted or locked-down builds).
			- GET /apps/:id – full security scan per device:
				- Enumerates installed apps, collects dumpsys package permissions and log/battery context for a touchSummary.
				- Uses detectSuspiciousApps + installer/source map to pick a bounded set of “interesting” packages (suspiciousApps) and only runs runDeepApkScan for that subset, keeping total scan time predictable even on phones with many apps.
				- Combines permission-based heuristics (scoreAppRisk) with deep scan results to produce riskByPkg + riskScoreByPkg.
				- Also returns installer-derived suspiciousApps list (via detectSuspiciousApps) for UI advice/warnings.
			- GET /suspicious-apps/:id – fast suspicious-apps endpoint:
				- Uses installerMap + quick name patterns to pick "interesting" apps, then fetches permissions only for those.
				- Returns a lightweight suspiciousApps list in ~5–15 seconds, used to update the UI immediately while /apps/:id runs deeper analysis.
			- GET /history/:id and POST /history/:id – per-device history storage:
				- History is stored under dataRoot (either %APPDATA%/SmartHubDiagnostics or .smarthub-data).
				- SavedRun includes: id, deviceId, deviceLabel, timestamp, counts (high/med/low), diagStages, diagDetails, textReport, optional screenTestImage.
			- GET /app-risk/:id/:pkg – on-demand single‑app risk view:
				- Computes permission-based risk and optionally runs deep APK scan for that package, returning combined detail.
		- POST /blue-test/flash, /blue-test/vibrate, /blue-test/sound, /blue-test/volume-max, /blue-test/touch, /blue-test/wake – quick ADB-based reaction tests for blue/blank-screen triage.
			- volume-max: sets media volume to max for clearer speaker testing.
			- vibrate: attempts direct ADB vibration first; falls back to mobile app test harness.
			- sound: auto-raises volume before launching the mobile app speaker test.
		- POST /test/sensors – sensor presence quick test; parses dumpsys sensorservice for accelerometer/proximity/light/gyro and returns a textual message for guided live checks.
		- POST /test/health – quick battery + memory snapshot; reads dumpsys battery and /proc/meminfo and summarizes level, temp, health, voltage and approximate RAM total/free.
		- History endpoints (not fully repeated here but important):
			- Uses dataRoot under %APPDATA%/SmartHubDiagnostics or .smarthub-data.
			- SavedRun includes: id, deviceId, deviceLabel, timestamp, counts (high/med/low), diagStages, diagDetails, textReport, screenTestImage.
		- SmartLink Agent APK (no-ADB helper):
			- GET /smartlink/agent-apk – serves the built android-smartlink debug APK as an attachment (application/vnd.android.package-archive).
			- Used by the UI when ADB install is not possible.
			- Depends on the APK being present at android-smartlink/app/build/outputs/apk/debug/app-debug.apk.
			- Note for packaging: if shipping as an installer, consider bundling a known APK build under the installed app folder and serving that, rather than relying on a dev-tree build output.

- src/adb.ts
	- Central ADB helpers.
	- `adb(...args)` – wrapper using execFileAsync(ADB, args, maxBuffer 25MB).
		- `listDevices()` – parses `adb devices -l` to DeviceInfo with connection type (usb/tcpip/emulator) and a structured DeviceConnection helper (host/port/usbPath).
	- `adbWithLimits(args, limits)` – wrapper that allows smaller timeouts/buffer limits for best-effort evidence collection (ex: small logcat snapshots).
	- `diagnosticSnapshot(deviceId)` – batched ADB snapshot used by /collect; includes three `dumpsys battery` samples (batteryDump + batteryDump2 + batteryDump3) for intermittency detection.
	- `screencap(deviceId)` – IMPORTANT FIX:
		- Uses execFile with `{ encoding: 'buffer' }` so stdout is a binary PNG Buffer.
		- This fixed earlier issue where screenshots were corrupt when treated as strings.
	- Other helpers: dumpsysDisplay, surfaceFlinger, logcatErrors, logcatWarnings, deviceProps, battery, storage, memoryInfo, listApps, packagePermissions, sensors, cameraInfo, connectivityInfo, hardwareFeatures.

Security / Apps Changes
- Deep APK scan:
	- Shared helper runDeepApkScan(deviceId, pkg) added in server (not reprinted here) to:
		- Run `adb -s id shell pm path pkg` → find APK on device.
		- `adb -s id pull` to a temporary file under the OS temp directory (no long‑lived apk-cache on disk); the temp APK is deleted immediately after scanning.
		- Call `python security-tools/apk_security_scan.py <apk>` which uses aapt to extract metadata and risk.
		- Parse JSON and return deep risk info.
	- /apps/:id selectively applies runDeepApkScan only to a bounded subset of suspicious apps, building deepScanByPkg without scanning every package.
	- /apps/:id merges deep risk with permission-based risk (assessAppRisk + classifyAppRisk + scoreAppRisk):
		- Picks worst severity between heuristic and deep scan.
		- Enforces minimum scores for deep risky/moderate results.
	- /app-risk/:id/:pkg uses the same helper for single-app detail.
	- On startup, the server deletes any legacy apk-cache folder under the SmartHub data root so old cached APKs no longer consume SSD space.
	- Net effect: deep APK scanning remains available for high‑risk apps, but disk usage is bounded and total scan time stays reasonable even on devices with hundreds of benign apps.

Notes for Future AI / Devs
- Respect existing style and naming; keep new diagnostics stages consistent with diagStages/diagDetails pattern.
- When adding new heuristics, prefer using existing ADB helpers in src/adb.ts rather than ad-hoc exec calls.
- Keep USB-only evidence collection read-only and time-bounded (avoid hanging or triggering USB/ADB instability).
- Any new binary data (images, logs) must be handled as Buffer, not string, to avoid corruption.
- For additional "no touch" workflows, extend no-debug modal and /connection-check rather than creating new top-level buttons.
- Backend binds to port 3333 by default; EADDRINUSE typically indicates the SmartHub desktop shell (or another node instance) is already running.
