SmartHub — BSOD / Blue-Blank Screen Help + Implementation Plan
Date: 2026-02-22

Context
- Enabling ADB (Android Debug Bridge) on a phone that is already stuck on a blue/blank screen, boot loop, or cannot boot Android is usually NOT possible, because ADB is an Android OS service.
- This is a “chicken & egg” problem: if Android cannot boot, ADB cannot start.
- Also: remotely toggling “USB Debugging” is intentionally blocked by Android security when the device is locked.

Goal
- Provide a practical, shop-friendly workflow to diagnose “BSOD / blue screen / blank screen / boot loop” phones using USB-only host signals and pre-boot modes.
- When available, leverage ADB/Fastboot signals; when unavailable, still give a useful “most likely cause” + confidence + next action.

Non-goals / Safety constraints (must be explicit in UI)
- Do NOT bypass lockscreen/encryption or attempt data extraction.
- Do NOT claim we can enable Developer Options / USB debugging remotely.
- Do NOT automate OEM unlock, bootloader unlock, or flashing.

Reality check: when ADB can be available
1) Android booted normally + USB debugging enabled + RSA trust accepted
   - ADB shows device state = “device”.
2) Android booted but trust not accepted
   - ADB shows “unauthorized” or “offline”.
3) Pre-boot environments where ADB may be available (device-dependent)
   - Custom recovery (e.g., TWRP) often exposes ADB in recovery.
   - Some OEM engineer/diagnostic modes may expose ADB.
   - Unlocked bootloader can allow “fastboot boot” of a diagnostic image (advanced; not universal).

Best diagnostic alternatives (without ADB)
A) Recovery Mode logs (stock recovery)
- Technician action: enter Recovery (varies by brand).
- What to look for:
  - “failed to mount /system” -> system partition corruption.
  - “can’t mount /data” -> storage failure or encryption/data partition issue.
  - repeated “E:” errors -> software/system problems.
- SmartHub approach:
  - We cannot read these logs without ADB, but we can guide the user with a checklist and record which option they selected.

B) Fastboot/Bootloader mode checks
- Technician action: boot to Fastboot/Bootloader mode.
- Host-side actions:
  - Run “fastboot devices” to confirm visibility.
  - Optional (advanced): “fastboot getvar all” when supported.
- Interpretation:
  - Fastboot visible but Android never boots -> likely System Errors (firmware/update/system corruption) and/or storage issues.

C) Low-level emergency modes (Qualcomm EDL / MTK preloader)
- If Windows sees devices like “QDLoader 9008”, “EDL”, “QHUSB”, “Preloader”, “BROM”, “VCOM”:
  - Android is not booted and ADB/fastboot won’t work.
  - High confidence of severe firmware/boot chain failure (System Errors), with possible storage/mainboard hardware failure.
- SmartHub scope:
  - Detect and label these modes (VID/PID/name heuristics) and provide the correct next-step guidance (authorized OEM service tools).

Practical “fix-it” concept (advanced, optional in future)
- Diagnostic boot image (unlocked bootloader required):
  - user runs “fastboot boot diagnostic.img”
  - image enables ADB and collects logs
- Notes:
  - This is NOT possible on locked bootloaders.
  - This must be treated as an advanced feature (shop-only) and must not be presented as universally available.


IMPLEMENTATION PLAN (SmartHub)

Phase 1 — Make USB-only triage excellent (no ADB required)
1) Backend: enrich /connection-check signals
   - Inputs we already have:
     - ADB devices list (including state)
     - Fastboot devices list
     - Windows Portable/MTP devices (WPD)
     - Windows transport-level USB devices + status + VID/PID hints
     - Stability sampling (anyChange / flapping)
   - Add/confirm:
     - Carry VID/PID + Windows ProblemCode consistently
     - Keep sampling defaults conservative (avoid long waits; allow deep mode)

2) Backend: map signals to clear “Part 1” cause categories
   - Output categories (the shop-facing list):
     - System Errors
     - Application Conflicts
     - Hardware Malfunction
     - Overheating
     - Insufficient Storage
   - Add “confidence” and “reasons[]” for explainability.
   - Important: USB-only cannot truly prove Application Conflicts / Insufficient Storage.
     - Only mark these as “likely” when you have multiple hints (e.g., camera OCR hint + connection pattern) or keep confidence low.

3) Frontend: make the no-debug modal actionable
   - Show:
     - ADB visibility
     - Fastboot visibility
     - MTP visibility
     - “Most likely reasons (Part 1)” + confidence
     - “Next best action” checklist (what to try next physically)
   - Always include limitations text:
     - “USB-only cannot read logs or storage usage. If possible, enable debugging or use recovery logs.”

Phase 2 — Add “pre-boot guidance” actions (still safe)
4) Guided technician steps (no automation)
   - Add simple decision prompts:
     - “Can you enter Recovery?” (Yes/No)
     - “Did you see ‘failed to mount /data’?” (Yes/No)
     - “Did you see ‘failed to mount /system’?” (Yes/No)
   - Use these responses to increase confidence for:
     - System Errors (system mount failures)
     - Insufficient Storage / storage failure (data mount failures)

5) Optional: camera-based visual module integration
   - Use the existing screen visual check:
     - blue/cyan dominance
     - OCR hints (overheat/security)
     - crack/banding/edge shadow hints
   - Map these to Part 1 categories:
     - Overheating: OCR overheat wording => medium confidence
     - Hardware Malfunction: crack/banding/edge shadow => medium/high confidence
     - Application Conflicts: only weakly hinted (avoid over-claim)

Phase 3 — Advanced / shop-only features (future)
6) Fastboot “getvar all” support
   - Add best-effort endpoint to run “fastboot getvar all” and parse common flags.
   - Guardrails:
     - If command fails, show fallback guidance.
     - Never request or store serials beyond what is already needed.

7) Diagnostic boot image workflow (only if explicitly desired)
   - Keep it behind an “Advanced” note.
   - Require technician to confirm:
     - bootloader is unlocked
     - they accept data/security risks
   - Do NOT ship or auto-download proprietary images.


Acceptance criteria (how we know it’s done)
- With ADB OFF and phone in normal consumer mode:
  - Tool still produces a Part 1 category with low/medium confidence and gives correct next steps.
- With fastboot-only devices:
  - Tool identifies System Errors with medium/high confidence.
- With EDL/Preloader devices:
  - Tool identifies System Errors with high confidence and gives correct OEM-service guidance.
- With stable MTP but no ADB:
  - Tool prioritizes Hardware Malfunction (display assembly) with medium confidence.

Known limitations (must remain visible)
- USB-only cannot read Android logs, storage free space, app lists, or temperature sensors.
- Some modes vary heavily by vendor; key combos and tool compatibility are not universal.
